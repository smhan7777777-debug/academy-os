# Academy OS audit — 2026-09-16

Historical baseline before the authorized v4 implementation. Current changes, verification and remaining production gaps are recorded in `SESSION_MEMORY_2026-09-16.md` and `README.md`; the findings below describe the original prototype.

Scope: this `academy-os` repository at commit `9bf48b1`, inspected without implementing product changes. This report is the only added repository file. The build regenerated ignored `dist/` output. Browser tests used isolated, disposable contexts; the user's browser records were not reset.

## Verdict

This is a presentable, browser-only workflow prototype. It is not yet an operational academy system, a backend application, or a functioning multi-agent service. README and CLAUDE.md acknowledge its simulated nature, but many individual screens promise behavior that the code does not enforce.

The approval-inbox concept and visual identity are worth retaining. The main risk is correctness: fabricated observations, approvals without required review, publication of the wrong text, lost payments across tabs, and untrusted input executing JavaScript were reproduced.

Recommendation: do not use it for real student records, accounting, or outbound communication in its current state. First repair workflow correctness and make the demonstration honest; then build the shared data and permission foundations; then connect one real workflow end to end.

## What was verified

- Read the repository documentation, tracked file inventory, app source, styling, shell, package configuration, and launcher. The repository was clean before the audit.
- `npm.cmd run build`: passed with Vite 6.4.3. Output: approximately 135 KB application JS / 44.8 KB gzipped, and 29.6 KB CSS / 6.8 KB gzipped.
- `node --check src/app.js`: passed.
- `npm.cmd audit --json`: zero known vulnerabilities reported. This is a dependency result, not an application security clearance.
- All 12 owner routes rendered at 1440 px and 390 px without uncaught page errors in the normal navigation smoke test.
- Inspected owner, teacher, parent, and student code paths; exercised role switching, lessons, reports, payments, approval/edit/hold, booking, inquiry, quiz, publication, and mobile navigation.
- Ran isolated behavioral probes for data corruption, failed storage writes, concurrent tabs, stored HTML injection, and keyboard focus.
- Additional width checks at 320, 768, and 1280 px covered today, students, lessons, timetable, billing, and website. Website content overflowed to 337 px at a 320 px viewport.
- Checked light and OS-selected dark color schemes and calculated contrast ratios from actual design tokens.

Limits: browser execution was in desktop Edge/Chromium, with mobile viewport emulation. This is not a Safari/iOS, Android-device, load, penetration, or complete accessibility certification. No live deployment URL, platform backend, provider credentials, or blueprint v2.1 server implementation was available in this folder. Their behavior is unverified. No messages were sent, no payments processed, and no deployment performed.

## Confirmed defects and proposed fixes

### 1. Untrusted booking names execute JavaScript — critical before external input

Evidence: `src/app.js:256` stores the booking name; `src/app.js:536` interpolates `l.name` into an HTML string without escaping. Submitting a harmless image error-handler marker as the name and opening Students executed the marker. This is a stored DOM XSS path within this local prototype, not evidence that a remote attacker has compromised a deployed service.

Fix: render user text through safe text bindings or `textContent`, audit every HTML interpolation, validate structured input, and add a restrictive Content Security Policy as defense in depth. A name validator alone is not an XSS fix. Add a regression test using markup-like names. OWASP recommends removing unsafe HTML sinks for plain text: https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html

Acceptance: names, notes, questions, and imported text display literally in every destination and never create executable DOM.

### 2. Untouched students become observed students — high

Evidence: opening the lesson view creates a draft for every student with present / homework submitted / average understanding (`src/app.js:548`). `saveLesson`, line 558, saves every created draft. Without touching any student, saving Class A created five observations and four parent-report drafts. The fifth report was correctly excluded for missing consent.

Fix: initialize each observation as unknown and distinguish viewed, edited, and explicitly confirmed records. Permit an explicit bulk confirmation with a visible student count. Save per scheduled lesson occurrence and student, with an intentional revision operation.

Acceptance: opening and saving an untouched class records no observations; one edited student cannot implicitly confirm the other four. Repeated save must not add duplicate lesson occurrences.

### 3. Absent students receive participation claims — high

Evidence: marking S1 absent still generated a report saying the student followed the lesson and submitted homework. `prepareReport`, line 183, uses comprehension and homework defaults irrespective of attendance.

Fix: make report generation conditional on actual observed fields and attendance. Absence must not imply participation. Store evidence references for each generated claim.

Acceptance: an absent student's report contains no unsupported classroom observations.

### 4. Required teacher review and owner authority are not enforced — high

Evidence: `approve`, line 152, and `guard`, line 172, do not check role, reviewer identity, review status, or an allowed transition. A teacher could open an unreviewed problem-set drawer and click its approval button; the document became `sent` with `reviewed` absent. The owner could also approve the seeded career report before the specified teacher reviewed it.

The teacher's Record button explicitly changes `role` to `owner` (`src/app.js:887`) and exposes the owner navigation and all class choices, including another teacher's class. There is no login or server authorization at all; the dropdown is a demonstration control.

Fix: enforce permissions and workflow transitions on the server. Keep teacher recording inside the teacher workspace, scoped to assigned classes. Review must identify the reviewer and exact document revision. UI button visibility should mirror these rules, not constitute them.

Acceptance: teacher sessions cannot approve as the owner or access other teachers' private data, even through direct API requests. Required review cannot be bypassed.

### 5. The approved text can differ from the published text — high

Evidence: content creation stores both `body` and `text` (`src/app.js:337`). Editing changes `body`; `afterApprove`, line 306, publishes the unchanged `text`. The browser test approved `OWNER_APPROVED_REPLACEMENT` and published `ORIGINAL_DRAFT_TEXT`.

Fix: use one structured revision as the source of each channel's final content. Preview the exact channel payload. Approval stores an immutable snapshot of content, recipients, channel, relevant source versions, and approver. Publishing consumes that snapshot.

Acceptance: the published bytes correspond to the reviewed channel payload. Editing after approval creates a new revision and cannot alter the historical approval.

### 6. Meaning-changing edits retain approval — high

Evidence: the `facts` comparison at lines 149–168 checks a sorted selection of number/name tokens. Changing an approved billing message from unpaid to paid retained `sent` status and logged a minor edit. Negation, meaning, names outside a narrow pattern, and number-to-field relationships are not covered.

Fix: require new approval for any change to outbound content initially. Later, exempt only narrowly defined formatting transformations that preserve a canonical structured payload. Keep historical sent content immutable.

Acceptance: a payment-status reversal or changed instruction always requires approval even if all digits are unchanged.

### 7. Timetable changes alter additional days and expose unpublished schedules — high

Evidence: a class has one shared `start/end` pair for all `days`. Replacing Monday with Tuesday 17:00 also moved Wednesday to 17:00 (`src/app.js:233`). Conflict checks inspect the requested day only (`src/app.js:224`). In the seeded data this silently introduces a Wednesday room collision with Class C at 18:00.

The public mock site and parent view immediately read the mutated class schedule (lines 654 and 782), while the distribution document is still awaiting approval and claims a future effective date.

Fix: model recurring sessions and dated exceptions separately; validate all resulting occurrences, teacher, room, student commitments, and consultation reservations. Maintain proposed, approved, effective, and published schedule versions.

Acceptance: changing one occurrence/day affects only the intended sessions; resulting collisions are blocked; public views respect the approved version and effective date.

### 8. Booking availability is not a reliable availability check — high

Evidence: `consultSlots`, line 247, returns occupied teacher times with a `teacherFree` flag rather than excluding them. Owner-only consultation could be a valid policy, but no owner calendar or room availability is checked. A Thursday 15:00 booking was accepted into Room 2 during Class B's 15:00–16:30 lesson, while its evidence claimed no scheduling conflict. Teacher availability is hardcoded to one teacher even for other classes.

Fix: specify required participants and resources, model appointment durations, and check full interval overlap. Use a transactional reservation/hold with expiry, cancellation and rescheduling. Recheck before confirmation.

Acceptance: two clients cannot confirm the same exclusive resource/time; occupied rooms are unavailable; the evidence reflects actual checks.

### 9. Browser tabs can silently lose financial changes — high

Evidence: the entire application state is independently loaded into each tab and written to one localStorage key (`src/app.js:95–104`). In tab A a 100,000 KRW payment was recorded. Holding an unrelated document in previously opened tab B overwrote the stored payment back to zero.

Fix: move canonical data to transactional server storage. Use version checks for concurrent edits and an immutable payment ledger. A prototype can add cross-tab stale-state warnings, but that is not a substitute for database concurrency controls.

Acceptance: stale writes are rejected or reconciled explicitly; unrelated updates cannot erase a payment.

### 10. Storage failures are reported as success — high

Evidence: `save()` suppresses all exceptions. A simulated quota exception still produced a payment-success toast while the persisted balance stayed unchanged. A parseable but invalid saved object (`{}`) crashed startup at the unvalidated `S.students.forEach` call and left the content view blank.

Fix: validate state schema and migrations; distinguish pending, persisted, and failed states; provide recovery/export for damaged local data. Production mutations should report success only after confirmed durable writes.

Acceptance: failed writes show a recoverable error, retain the input, and cannot display successful persistence.

### 11. Staff and policy controls overstate their effects — medium/high

Evidence: turning the report employee off still generated reports. `S.hired` is displayed and toggled, but generation paths do not consult it. `autoAttendance` is saved and changes the toast; there is no corresponding automatic attendance-notification execution path. Optional makeup work can be generated while that employee is off.

Fix: define enablement semantics and enforce them in job creation/execution. For unimplemented capabilities use a clear unavailable/demo state instead of a working switch. Show last run, next run, last result, failures, and settings for real workers.

### 12. Hold does not mean tomorrow — medium

Evidence: `hold`, line 160, changes status only. An urgent document stays in the urgent tier and remains actionable; no `resumeAt` or daily scheduler exists, despite the toast saying it moved to tomorrow morning.

Fix: store a resume timestamp, hold reason, and an independent deferred queue. Surface urgent deadlines separately.

### 13. Some public controls and inquiry completion do not work as described — medium/high

- Turning teacher visibility off does not hide teacher names; the mock class rendering ignores `live.teachers` (lines 654, 688, 857).
- Approving an inquiry answer fills a knowledge slot but never updates the originating visitor conversation. The original remains an escalation placeholder although the document says `sent` (lines 269–275, 308).
- The repeat-booking form can display a valid new slot while internal `webDraft.slot` is empty, causing the next submission to say the slot just filled (line 851).
- FAQ lookup returns the first keyword match. For example, questions containing both tuition and refund terms can select tuition before the empty refund slot. It is not semantic question answering.

Fix: make visibility a rendering/publication rule; model conversations and answer delivery explicitly; clear and rerender form state atomically; use deterministic supported-intent routing with escalation for mixed or ambiguous questions.

### 14. Quiz placement and result ownership are wrong — medium/high

Evidence: `scoreLevel`, line 323, ignores grade. An elementary Grade 5 math test with five correct answers recommends the middle-school Grade 2 class. Every booking attaches the last quiz result in the entire state (`src/app.js:263`), including a new applicant who never selected that result.

Fix: use an educator-reviewed question bank and placement rules by grade, subject, prerequisites, and actual offered classes. Attach a specific assessment session only with an explicit link to that applicant. Describe the current version as a sample quiz, not a validated AI diagnosis.

### 15. Operational facts and derived work drift apart — medium/high

Evidence: attendance/homework saves do not update `signals`; full payment leaves the seeded `payLate` signal set; remaining lessons are static counters unaffected by lesson saves. Wrong-answer edits change the exam without source-version invalidation of derived documents (`src/app.js:845`). Approved problem-set evidence still named a question removed from the wrong-answer list. Historical approved snapshots should be retained, but the app provides no supersession/recalculation path.

Fix: derive current signals from dated authoritative records with defined time windows. Separate historical evidence from current state. Use dependency/source revisions to regenerate or mark affected pending work outdated, and clearly identify superseded published work.

### 16. Time, metrics, and provenance are simulated but often presented operationally — medium/high

Evidence: business date is fixed at 2026-09-14, booking slots are a fixed four-day array, morning preparation is a one-time boolean, while audit timestamps use the actual UTC clock. Logs display UTC string slices without Korea-time conversion. Seeded visit/lead counts are reused across weekly/monthly summaries. Estimated saved time sums all prepared documents, including stale/uncompleted work, rather than measured completed work. Initial navigation badges render before morning preparation, so a fresh page can show six pending documents but no badge or bell indicator.

Fix: isolate demo fixtures and an injectable clock from real operation; use Asia/Seoul business dates and UTC instants for storage. Build metrics from dated events with explicit definitions, source, attribution, and measurement period. Render preparation results before counts.

### 17. Legal and business-support content needs correction and provenance — high before reliance

Evidence: `BIZ_FAQ` at line 373 reduces post-start tuition refunds to daily proration. That is not a safe general statement: official Korean guidance includes thresholds based on elapsed teaching time for voluntary withdrawal from courses of up to one month, with different treatment for longer terms and other reasons. Source: https://www.easylaw.go.kr/CSP/CnpClsMain.laf?ccfNo=2&cciNo=3&cnpClsNo=2&csmSeq=1140

Other tax dates, a specific subsidy/deadline, advertising-law claims, purported news sources, and expert connections are hardcoded without verifiable records or operational integrations. This audit did not certify each legal/tax claim. Administrative documents are generic placeholder paragraphs, not completed legal forms (`prepareBizDoc`, line 375).

Fix: replace unverified claims with clearly identified examples until reviewed. Store jurisdiction, applicability, official source URL, effective date, reviewer, and review deadline for each rule/template. Implement refund calculation as a tested deterministic policy with appropriate professional review. Never infer subsidy eligibility from the presence of a sample card.

## UI and interaction recommendations

The forest/cream/sage identity is coherent and should be retained. Rounded cards, restrained icons, Korean typography, and confirmation/evidence concepts form a usable starting point. The problem is task hierarchy and interaction, not absence of decoration.

1. Put the approval list near the top. At 1440×1000 the inbox heading was about 1,391 px below the page top. At 390×844 it was about 2,295 px down; the entire home screen was about 4,952 px tall. Introductory explanations, four KPIs, triggers, and four quick-work cards precede the core task. Replace this with a short status line, 3 useful counts, then actionable inbox rows. Move learning content and promotional explanations to onboarding/help.
2. Make task state explicit. Separate teacher review, owner approval, deferred, delivery failure, and completed states. Show exact recipient/channel, change summary, source age, and blocking reason. Treat evidence viewing as a normal part of high-impact approvals.
3. Simplify navigation around Today, Students, Lessons, Billing, and Website. Group content/business support/settings progressively. Keep the employee metaphor as secondary operational detail. The owner should not have to interpret 18 employee cards to perform one task.
4. Implement real search. The header search is a decorative span in `index.html:28`. Add keyboard-accessible student/guardian/class search with useful result destinations. Remove or clearly label inactive demo controls.
5. Make mobile interactions task-specific. Keep sticky primary actions, short headers, and a compact/mobile navigation pattern. At 390 px the reset label wraps awkwardly and the floating manager can cover lesson inputs. Use student summary cards or intentional horizontally scrollable tables. Fix the narrow 320 px website overflow.
6. Increase legibility. Gold `#BF9E62` on white is about 2.54:1; muted `#75847A` on white is 3.93:1 and on the page background about 3.54:1. These are below the 4.5:1 requirement for ordinary text. OS-selected dark mode leaves white text on green action buttons at about 2.34:1 because the dark text override only targets an explicit data-theme attribute. Preserve gold as decoration or darken it for text. Source: https://www.w3.org/WAI/WCAG21/Understanding/contrast-minimum
7. Improve keyboard and assistive-technology support. A drawer leaves focus behind the overlay; Tab can reach background actions. The dialog has no accessible name. Student rows are mouse-clickable without equivalent keyboard links; many fields lack associated labels. Chips have visual selection without equivalent state semantics. Use proper labels, accessible dialogs, focus containment/restoration, and semantic selection controls. Source: https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum
8. Use a comfortable mobile target size. Lesson chips measured about 30 px high and approval buttons about 34 px. Aim for roughly 44 px primary touch targets as a usability target; this observation alone is not a claim that every smaller control violates WCAG.
9. Reduce repeated instructional prose. Show short Korean task labels such as `검토할 서류 6건`, `강사 검수 필요`, `수정 후 결재`, and `내일 다시 보기`. Put long policy explanations into expandable help. Retain the serif for selected headings, with clear sans-serif operational text and tabular numbers.

## Proposed backend and frontend structure

There is no existing backend to refactor. The first backend should be a modular application with a relational database and a durable background worker. Eighteen product personas do not require eighteen independently deployed services.

### Boundaries

- Frontend: role-specific pages and reusable components; forms and rendering only, with typed requests/responses.
- API/domain: authoritative validation, authenticated actor and academy membership, business rules, transactions, approval transitions, and public/parent projections.
- Database: academy-owned records, constraints, revisions, payment ledger, immutable approval snapshots, audit events, job/outbox records.
- Worker: scheduled preparation, AI draft jobs, approved delivery/publication, retry and reconciliation. Browser navigation must not schedule business work.
- Adapters: agent1000, messaging, payments, model providers, and file storage behind explicit contracts, with sandbox/production modes.

Suggested modules: identity/academies; students/guardians/enrollments; classes/rooms/sessions; attendance/lesson records; assessments/question bank; billing/payments; bookings/conversations; documents/reviews/approvals/delivery; website/knowledge/content; audit/jobs/integrations.

Use TypeScript or comparably explicit schemas and tests. Split `src/app.js` by these boundaries. Rendering currently replaces the whole view and rebinds handlers for routine interactions, coupling UI, state, and side effects. A component frontend can improve maintenance; changing frameworks alone will not repair the business rules. Preserve the current Vite setup where practical while moving rules into testable modules.

### Data model essentials

| Group | Essential records |
|---|---|
| Identity | academies, users, memberships, roles, teacher assignments, verified guardian/student links, consent records |
| Academy operations | students, guardians, enrollments, classes, rooms, recurring schedules, dated lesson sessions, observations |
| Learning | assessments, items, responses, question-bank rights/provenance, problem-set versions and reviews |
| Finance | invoices, invoice items, payments, allocations, adjustments/refunds, provider events |
| Communication | booking requests, reservations, conversations, messages, recipient identities |
| Approval/execution | documents, document revisions, review records, approval snapshots, delivery attempts, outbox jobs |
| Governance | audit events, policy versions, knowledge versions, integration configuration, run/error records |

Every academy-owned row needs tenant ownership, foreign keys, and an authorization policy. Derive tenant and actor from verified sessions, never a submitted role dropdown. Parent reads must verify the guardian/student link; teacher reads must verify assignments. PostgreSQL row-level security can provide additional protection when correctly configured; owners and bypass roles require special care. Source: https://www.postgresql.org/docs/17/ddl-rowsecurity.html

Store monetary amounts as integer KRW. Separate invoice totals from immutable payment events and allocations. Enforce unique provider event/idempotency keys. Keep adjustments explicit rather than rewriting historical financial facts.

### Approval and delivery

Recommended document path: draft → teacher review when required → owner review → approved revision. Held, rejected, stale/superseded, and cancelled are explicit alternatives. Approval and delivery are separate records: approved → queued → processing → delivered, or failed/retry/reconciliation required. Do not call a document delivered merely because an approval succeeded.

Within one database transaction, record the approval snapshot and an outbox job. The worker uses that snapshot, rechecks conditions such as paid invoices or withdrawn consent where applicable, uses provider idempotency where available, and records actual provider outcomes. For uncertain outcomes, reconcile rather than blindly resending. Claiming exactly-once delivery across external providers would be inappropriate without their guarantees.

### AI work

Start with one grounded report workflow. A real run should record academy, job, input record versions, permitted data, template/prompt/model version, output schema, evidence, cost/latency, and failure status. Separate deterministic operations (money, dates, conflicts, permissions, score calculations) from language generation. Validate model outputs and require review before external action. Job triggers should honor employee enablement and academy policy.

Build an evaluation set for missing records, absent students, changed balances, ambiguous questions, unknown facts, and age/grade mismatches. Do not connect the existing unsafe template flows to an LLM and assume they become correct.

## Delivery order and acceptance gates

1. **Prototype correctness and honest scope.** Fix injection, unknown observations, review/role checks, approved-content mismatch, semantic reapproval, timetable/session modeling, misleading controls, and false completion copy. Add focused regression tests for these demonstrated failures. Gate: no known reproduced critical/high workflow defect remains in the intended demo flows.
2. **Shared data and access foundation.** Add API, database migrations, real sessions, academy scoping, guardian/teacher access rules, transactional mutations, audit log, recovery and backup/restore verification. Gate: cross-academy access fails; concurrent changes cannot erase each other; saved means durable.
3. **One complete operational slice.** Teacher records one dated lesson → grounded draft → teacher review if required → owner approval → one real message → correct parent view. Gate: recipient sees the exact approved content once under normal delivery; retries/uncertain outcomes are handled explicitly; changes to source facts are detected.
4. **Daily-work UI redesign.** Bring approval work into the first screen; implement search and role-specific navigation; address keyboard accessibility, mobile layouts, contrast, and actionable failures. Gate: task-based observation with an owner and teacher, plus keyboard and physical-phone checks.
5. **Expand by demonstrated need.** Reconciled billing, conflict-safe scheduling/booking, onboarding/imports, assessments, and real website integration. Add content/business-support breadth only when sources and underlying workflows exist.

Do not estimate completion solely from the number of screens. Provider access, platform API contracts, financial policy, guardian identity, and migration requirements materially affect the production schedule. Those choices need concrete design before a defensible build estimate.

## Validation to preserve during implementation

- Untouched records stay unknown; absence does not become participation.
- Teachers cannot access another class or act as owner; parents cannot access an unrelated student; academies cannot access each other.
- Required review is tied to the approved revision; edited payloads require fresh approval.
- Published/delivered content equals the snapshot, including recipient/channel.
- Payments are durable and duplicate provider events do not double-credit balances.
- All affected timetable occurrences/resources are checked; booking races have one valid winner.
- Failed persistence is visible; corrupt local legacy data has a recovery path.
- User text cannot execute HTML/JavaScript.
- Held items return at their recorded time; disabled jobs do not run.
- Metrics reflect actual periods/events; demo metrics remain visibly examples.
- Keyboard focus stays in dialogs; ordinary text meets contrast requirements; mobile primary actions remain reachable.

The existing positive behavior should also be preserved: consent-based exclusion of the seeded student's report draft, billing-draft invalidation after a payment, student/billing filters, visible source/evidence sections, and normal route rendering.
